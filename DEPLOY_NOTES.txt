DEPLOY
  Order doesn't matter much here (no cross-file dependency like the
  secrets/ migration had) — upload all 10 in one pass. The two new
  .htaccess files should land in the same upload so the protection isn't
  briefly absent.

STAGING TESTS TO RUN (see the full Phase 1F report for the complete list)
  - Host A can still select legitimate same-bounty winners normally.
  - Submitting a winner_submission_id that belongs to a DIFFERENT bounty
    is silently rejected: no status change, no certificate, no XP, no
    notification/email for that submission.
  - Same check for feedback: a host cannot set feedback on another
    bounty's submission; legitimate same-bounty feedback still saves.
  - admin/bounty-submissions.php's feedback save still works for any
    submission regardless of bounty (admin is platform-wide by design).
  - admin/settings.php: save fails with a missing/invalid CSRF token,
    succeeds with a valid one; same for the test-email form.
  - bounty-host-dashboard.php: "Close Bounty" / "Archive" links still
    work normally when clicked from the dashboard itself; a bare/stale
    link without a valid csrf_token is rejected.
  - Each cron endpoint still accepts its correct key and rejects a wrong
    one.
  - Request database/ and includes/ directly over HTTP — both should be
    blocked (no file listing, no file content returned).

No secrets, credentials, migrations, or Stellar code are touched by
anything in this package.
